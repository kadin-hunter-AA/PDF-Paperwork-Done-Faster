# Advanced PDF capabilities — implementation and acceptance plan

Status: October 15, 2026 integration checkpoint. Restricted local OCR, existing-text-field filling, certificate-signed-copy export and structural-redaction preview/export now have product commands and passing engine/session/UI evidence. Exact supported subsets and outstanding release gates are in CAPABILITIES.md and BUILD-STATUS.md. They do not provide general form authoring, arbitrary-font editing, full redaction compatibility, certificate-trust verification or batch OCR. The initial architecture/dependency research below is retained as planning history; statements about the pre-integration baseline are historical.

The private Python runtime is now explicit and bundled by App.Desktop.csproj, with pinned libraries and notices. No cloud service or paid SDK was configured. Cloud processing remains unavailable unless a later implementation obtains explicit per-operation consent. The native PDFium viewer and established checkpoint architecture remain intact; companion jobs receive disposable input copies, never authoritative checkpoints or source PDFs.

## Planning baseline and engine boundary (before companion integration)

The desktop references `App.Core`; the worker references `App.Core` and `App.Pdfium`, and owns all PDFium handles behind serialized JSON-line requests. `DocumentSession` provides per-document serialization, worker restart, immutable hashed checkpoints, monotonic session revisions, undo/redo, recovery, candidate reopen validation, and guarded publication. Every new mutation should use this path unless a signature-specific publication flow explicitly requires a different commit contract.

PDFium chromium/8086 is already used for page rendering and the pinned form-fill lifecycle. `EngineForms.cs` initializes `FPDFDOC_InitFormFillEnvironment`, registers pages, and calls `FPDF_FFLDraw`; a frozen fixture proves one widget appearance survives viewer/print rendering and ordinary save/reopen. This is appearance evidence only. The adapter currently has no field discovery, input, validation, calculation, appearance regeneration, or form-save operation. XFA is explicitly unsupported. `App.Pdfium` already has page-object enumeration, basic edits, markup, page operations, save/reopen, and signature-count detection, but no OCR, semantic secure-redaction workflow, cryptographic certificate-signing workflow, or signature-trust validation. Ordinary edits rewrite the PDF through the existing PDFium checkpoint path and invalidate existing signatures on the edited copy.

Keep native handles and third-party PDF calls in the worker/adapter boundary. Extend the protocol with explicit operation names and bounded arguments; never put document text, passwords, certificate secrets, or recognized page text in recovery metadata or logs. Use candidate files and independent validation before publishing. Failures, cancellation, timeouts, unsupported structure, and stale revisions must leave the last committed checkpoint and source intact.

### A. Shared prerequisite: capability and document classification

1. Add a worker inspection operation that reports only bounded feature flags needed to decide whether a requested workflow is eligible: page count/rotation, existing signature fields and cryptographic signatures, AcroForm/XFA type and field inventory summary, encryption, and relevant structure/risk indicators. Keep user-facing details useful without exposing arbitrary file contents.
2. Make each feature declare its accepted input profile and its own preflight. Do not infer that “PDFium opened it” means a document is safe to edit. Preserve conservative refusal for unsupported tagged, encrypted, signed, malformed, or structurally complex cases until a proof covers them.
3. Add synthetic fixtures for expected successes and refusals, plus immutable input hashes and independent output inspection. The existing frozen `fixtures/` remain reference data; new fixtures should be reviewed/versioned through the corpus workflow.

Acceptance: the worker reports stable classifications across reopen; malformed/hostile cases time out or fail closed; no preflight mutates the source; classifications do not claim certificate trust or redaction success.

### B. OCR for scanned documents

**Engine assessment.** The existing PDFium text extraction (`Extract` / `ExtractTextLayoutAsync`) reads a PDF text layer; it does not recognize pixels. PDFium rendering can supply bounded page bitmaps, so it is a viable raster source, not an OCR engine. OCR requires a separate local recognition engine and a text-layer writer. Keep recognition and OCR text out of the main UI process. Do not assume a native Windows OCR API meets redistribution, language-pack, offline, or servicing requirements without research.

1. Research and compare a locally bundled OCR engine (initial candidate: Tesseract with explicit language-data packages) against Windows OCR APIs for Windows 11 x64, language coverage, rotation/layout/deskew support, accessibility, package size, offline behavior, security updates, and redistribution obligations. Cloud OCR may be offered only as an optional per-use operation after explicit disclosure and affirmative consent for that individual document/job; do not upload automatically or reuse consent. Personal/internal release is the initial distribution target.
2. Add a worker-side OCR adapter with page/pixel/time/memory bounds, cancellation, page-region output, confidence values, and language selection. Generate candidate searchable PDFs by adding an invisible text layer aligned to page-space coordinates; retain original pixels and page geometry. Do not silently replace or modify the source scan.
3. Add UI for current page and selected page range, language choice, progress/cancel, and a preview of recognized text/boxes before applying. Mark OCR output as machine-recognized and let the user correct it using the separately scoped text workflow.
4. Route “apply OCR” through `DocumentSession` as a new committed checkpoint with undo/redo, recovery, Save As, save/reopen, and source-hash checks. Use a new candidate pipeline if the selected writer cannot preserve required structures; avoid pretending that existing PDFium `SaveCandidate` alone inserts a valid invisible text layer.

Acceptance: independently verify that source image pixels render unchanged, text extraction returns expected words and boxes within defined tolerances, search/copy works after reopen, language/rotation cases meet declared support, cancellation leaves source/checkpoint unchanged, and failures do not publish partial output. Record false-positive/false-negative samples and disclose OCR uncertainty. Cloud mode must display the exact document/job scope and obtain affirmative consent each use; a canceled consent sends no bytes.

### C. Fillable AcroForm fields

**Engine assessment.** The current PDFium form-fill ABI proves widget rendering. PDFium's form-fill APIs are a plausible local starting point for widget enumeration and value input, but this repository has not yet bound or validated those APIs. Authoring fields, XFA, JavaScript calculations, complex button states, and broad appearance fidelity remain unknown. Research the pinned PDFium header/export surface first; do not assume rendering support implies correct value persistence.

1. Prove a narrow field inventory/value round-trip in `EngineProof` before exposing UI: text fields, check boxes, radio groups, choice fields, required/read-only flags, field names and widget rectangles. Determine support for values, appearance generation, save/reopen, and UTF-16 content from actual pinned exports/header. Refuse XFA and unsupported field/action types.
2. Add worker operations for field listing and setting values, with revision-bound stable identifiers and strict bounds. Disable or reject document JavaScript/actions; do not execute arbitrary document scripts. Reopen a candidate with PDFium and an independent parser, and render widgets through the existing form-fill path before accepting.
3. Add a form panel that clearly distinguishes filling existing fields from creating/editing form widgets. Provide keyboard/accessibility controls, required/error feedback only where semantics are proven, and a clear unsupported-field explanation.
4. Commit successful fill operations through the existing full-checkpoint `DocumentSession` path. Preserve unsigned `/Sig` fields and other document structure where the proof demonstrates it. Existing signed documents require the current explicit edit-copy consent and signatures will be invalidated by ordinary editing; never characterize this as a signed update.

Acceptance: exercise text, checkbox, radio, dropdown/list, date-like text, read-only, required, Unicode, duplicate/inherited field names, rotated widgets, stale IDs, malformed appearances, and unsupported XFA/actions. Verify values and appearances after save/reopen in independent readers, preserve unrelated form fields and page structure, verify undo/redo and recovery, and reject/cancel without changing source. Broader field types remain hidden until their specific cases pass.

### D. Verified permanent redaction

**Engine assessment.** The current highlight/underline/strikeout operations are annotations; drawing an opaque rectangle or adding markup is not redaction. PDFium object enumeration/removal can support a limited proof for simple page objects, but deleting visible objects alone cannot prove removal from shared Form XObjects, clipping/content streams, hidden text, metadata, attachments, alternate renderings, or prior revisions. A dedicated sanitizer or a rigorously bounded structural rewrite is required. Treat this as a new redaction engine/workflow, not an extension of the annotation path.

1. Define a threat model and supported input subset before coding. Decide which data must be removed (visible content, text extraction, object/resource streams, metadata, attachments, OCR layers, prior revisions, embedded files). Default to rejecting signatures, encryption, portfolios/attachments, XFA/forms, tagged content, layers, incremental-update histories, unsupported filters, and ambiguous page geometry until each is covered.
2. Research maintained structural sanitization libraries and independently inspectable workflows. Candidates to evaluate include a dedicated commercial PDF SDK and open-source parser/writer combinations; compare recursive resource reachability, shared-object handling, stream/object garbage collection, incremental-save avoidance, independent validation, Windows x64 distribution, and licenses. PDFium alone is not an accepted security claim unless the implementation proves full removal for its declared subset.
3. Build a proof harness that applies redaction regions to source copies, removes intersecting visible objects and all corresponding shared/nested resources, writes a fresh non-incremental file, and validates both rendered appearance and semantic absence. Include text extraction, raw object/stream scanning, metadata/attachment checks, independent parser inspection, and adversarial cases (duplicate text, ligatures, invisible text, clipped text, images, reused forms, OCR layers, rotated/cropped pages, layers, annotations, and prior revisions).
4. UI must separate “mark area for redaction” from “apply permanent redactions.” Preview the exact regions and affected pages; warn that output is a sanitized new copy. Never make the source the destination. No supported claim until output passes all independent checks for every declared input class.

Acceptance: no target text or pixels remain in rendered output; target strings/glyph encodings and image regions are absent from extracted and raw reachable content; removed resources are not retained elsewhere; metadata/attachments/revisions follow the declared sanitization policy; unaffected content is preserved within defined tolerances; independent tools cannot recover redacted material; refusal, cancellation, crash, and destination conflict preserve source and publish no partial final. Retain a signed-off evidence report per supported class. “Verified permanent redaction” must remain unavailable if any inspection path is inconclusive.

### E. Certificate-based digital signatures

**Engine assessment.** Existing code detects signature fields/signatures and protects signed originals, but the current PDFium save/rewrite path invalidates signatures and does not create cryptographic signatures. Certificate signing requires a signing-capable PDF library that writes an interoperable PDF signature dictionary and byte-range in an incremental update, plus certificate/key handling and independent validation. PDFium can continue to render/inspect but is not the signing engine on current evidence.

1. Research candidate signing SDKs (including commercial PDF SDKs and a .NET-compatible signing library such as iText) for PAdES/CMS support, Windows x64 and offline operation, certificate-store/CNG/PKCS#11 integration, timestamp authority and revocation/LTV support, licensing for personal/internal use, and security update commitments. Do not select a dependency until redistribution terms and threat model are reviewed. Separate visible appearance from cryptographic signature creation.
2. Define v1 scope: certificate source (Windows certificate store or user-selected PFX), supported key algorithms, password prompt/handling, timestamping policy, signature profile, trust/revocation limits, and whether co-signing or certification signatures are included. Secrets must stay in protected OS/key-provider flows where possible; never persist passwords/private keys in settings, recovery, logs, or checkpoints.
3. Implement signing as a specialized publish transaction over a stable committed checkpoint. Freeze edits during signing; create a new destination candidate; sign with an incremental update; independently reopen and validate byte ranges, CMS signature, certificate chain status as available, and document modification state. Publish only after validation. Preserve existing signed source and do not route final signing through ordinary PDFium `SaveCandidate`, which rewrites the file.
4. Add UI that reports signer identity, signing time source, certificate validity/trust/revocation status and validation limits separately. Signing success must not imply trusted signer or valid timestamp if those checks were unavailable. Any later edit must clearly report that prior signatures no longer validate.

Acceptance: use test certificates and independent validators/readers; verify byte-range integrity and visible appearance, reopen stability, unsigned/signed modification detection, invalid/expired/untrusted/revoked certificate cases, canceled PIN/password/credential prompts, timestamp failure, worker crash, and destination conflicts. Test multiple signatures only if included in v1. Never claim trust validation beyond the configured chain/revocation/timestamp checks.

## Cross-cutting delivery gates

1. **Research and decisions:** produce a dependency comparison and license/security review before adding OCR, sanitization, or signing packages. Record versions, native binaries, language packs, notices, update path, and deployment footprint. Cloud OCR consent and data handling are per use. Initial release is personal/internal; any broader redistribution needs a fresh license and package review.
2. **Engine proof:** each feature starts in a separate proof harness with real, versioned fixtures and independent inspection. Engine capability is not UI acceptance.
3. **Worker/session integration:** add bounded protocol requests and revision checks; keep native operations isolated; make cancellation/timeout behavior explicit; preserve immutable checkpoints and recovery. Mutations must be reversible until successful validation and durable commit.
4. **UI acceptance:** expose only the proven subset. Keep add-text, existing-text replacement, markup, form filling, OCR, redaction marking/application, drawn signatures, and certificate signatures as distinct concepts and commands. Add accessible keyboard/UI flows, preview, progress, and accurate refusal messages.
5. **Release evidence:** run the existing core completion gates and then clean-machine Windows 11 x64 installed acceptance for the integrated product. Capture build/dependency identity, worker/session/UI results, source/output hashes, independent reopen/check results, device/scaling/accessibility checks, and package/redistribution review. Advanced feature proof does not waive existing P0, install, or clean-machine gates.

## Decisions required before implementation

- OCR v1 language set and local engine; whether optional cloud recognition is offered, with explicit per-document/per-use consent and disclosed provider/retention terms.
- Form v1 field types and how unsupported actions/calculations are presented.
- Redaction threat model and exact content classes the “permanent” claim covers; acceptance reviewer and independent tools.
- Signature v1 certificate source, signature profile, timestamp/revocation expectations, and trust-validation wording.
- Third-party dependency/license approvals and personal/internal package boundary.

The user has not yet chosen paid versus free dependencies or OCR languages; the comparison above keeps those decisions open and does not imply a purchase or license approval.

These decisions can be resolved after dependency research and proof prototypes. Until each feature's acceptance gate passes, retain the current capability statement that OCR, form authoring/filling, verified permanent redaction, and certificate signatures are unavailable.
